**Amass(OWASP Amass)는 공개 정보와 네트워크 정찰을 활용해 조직의 외부 노출 자산을 발견하고, 자산 사이의 연결 관계를 정리하는 오픈소스 보안 도구입니다.**

특히 **서브도메인 열거(Subdomain Enumeration)**로 많이 알려져 있지만, 도메인 목록을 찾는 것에서 더 나아가 IP 주소·네트워크·인증서 등의 관계를 분석하는 **공격 표면 파악 도구**입니다. [OWASP 공식 소개](https://owasp.org/www-project-amass/)

**1. Amass가 필요한 이유**

기업의 인터넷 서비스는 대표 홈페이지 하나로 끝나지 않습니다. API 서버, 개발 서버, VPN, 메일 서비스 등이 서로 다른 주소에서 운영될 수 있습니다.

다음은 가상의 예시입니다.

| 주소                | 추정 용도     | 보안 관리에서 확인할 사항       |
| ----------------- | --------- | -------------------- |
| `www.example.com` | 대표 홈페이지   | 정상적으로 관리되는 서비스인가?    |
| `api.example.com` | API 서비스   | 인증과 접근 제한이 적용되어 있는가? |
| `dev.example.com` | 개발 환경     | 외부 노출이 의도된 것인가?      |
| `old.example.com` | 이전 서비스    | 사용 종료 후 방치되지 않았는가?   |
| `vpn.example.com` | 원격 접속 서비스 | 담당자와 관리 정책이 명확한가?    |

여기서 주소 이름은 용도를 추정하는 단서일 뿐입니다. `dev`라는 이름만으로 개발 서버라고 확정할 수는 없습니다.

보안 담당자가 대표 홈페이지만 점검하면, 다른 주소에서 운영되는 서비스를 놓칠 수 있습니다. Amass는 이런 **점검 대상의 누락을 줄이기 위한 자산 조사**에 활용됩니다.

**공격 표면(Attack Surface)**은 공격자가 접근하거나 상호작용할 수 있는 지점의 집합입니다. 외부에 노출된 웹사이트, API, 원격 접속 서비스 등이 여기에 포함됩니다. 자산을 발견했다고 곧바로 취약한 것은 아니지만, 존재를 알아야 관리 여부를 확인할 수 있습니다.

**2. 어떤 정보를 다루는가?**

Amass의 자산 모델은 발견한 개별 정보뿐 아니라 정보 사이의 관계도 표현합니다. 대표적인 대상은 다음과 같습니다. [Open Asset Model 공식 문서](https://owasp-amass.github.io/docs/open_asset_model/)

| 정보         | 의미                              | 조사에 활용하는 방식      |
| ---------- | ------------------------------- | ---------------- |
| 도메인·FQDN   | `api.example.com` 같은 완전한 도메인 이름 | 서비스 주소 식별        |
| IP 주소      | 도메인이 연결되는 네트워크 주소               | 호스팅 위치와 연결 관계 확인 |
| DNS 정보     | 이름과 IP 또는 다른 이름의 연결 정보          | 서비스 구성 파악        |
| 네트워크 대역    | IP 주소가 포함되는 주소 범위               | 인프라 관계 분석        |
| 자율 시스템·ASN | 인터넷에서 네트워크를 운영하는 단위와 식별 번호      | 네트워크 운영 주체 확인    |
| 도메인 등록 정보  | 등록기관 등 도메인 관련 정보                | 자산 귀속 판단의 단서     |
| TLS 인증서    | 인증서에 기재된 이름·발급자·유효기간 등          | 관련 서비스와 이름 확인    |
| URL·서비스 정보 | 웹 주소와 서비스 관련 정보                 | 추가 점검 대상 정리      |

**지원하는 정보 유형이 모두 자동으로 수집되는 것은 아닙니다.** 실제 결과는 활성화한 수집 기능, 외부 데이터 소스, 인증 정보, 조사 범위에 따라 달라집니다.

**3. 동작 원리**

Amass의 수집 과정은 **하나의 발견을 다음 조사의 입력으로 사용하는 방식**으로 이해하면 됩니다.

예를 들어 도메인을 발견하면 DNS 정보를 조회할 수 있고, IP 주소를 얻으면 해당 IP의 등록 정보나 역방향 DNS 정보를 확인할 수 있습니다. 이런 과정을 통해 처음 입력한 정보에 관련 정보를 덧붙입니다. 공식 문서는 이를 자산의 **변환·확장(Transformations)** 과정으로 설명합니다. [수집 파이프라인 공식 문서](https://owasp-amass.github.io/docs/configuration/transformations/)

개념적인 작업 순서는 다음과 같습니다.

1. **조사 범위 지정**: 소유하거나 점검을 허가받은 도메인을 정합니다.
2. **정보 수집**: 외부 데이터 소스와 허용된 정찰 방법으로 자산 후보를 찾습니다.
3. **정보 보강**: DNS, IP, 등록 정보 등 관련 정보를 확인합니다.
4. **관계 정리**: 어떤 이름이 어떤 IP나 서비스에 연결되는지 기록합니다.
5. **결과 검토**: 실제 소유 자산인지, 현재도 유효한지, 점검 범위에 포함되는지 판단합니다.

발견된 관계는 추가 조사의 단서이며, 소유권을 자동으로 확정하는 증거는 아닙니다.

**4. 수동적 정찰과 능동적 정찰**

Amass는 공개 정보 수집과 능동적 정찰을 결합합니다. 이 둘을 구분해야 실행 시 발생하는 통신과 결과의 의미를 이해할 수 있습니다. [Amass 공식 저장소](https://github.com/owasp-amass/amass)

| 구분           | 수동적 정찰(Passive)               | 능동적 정찰(Active)           |
| ------------ | ----------------------------- | ------------------------ |
| 기본 개념        | 제3자가 이미 수집한 정보 조회             | 대상 관련 인프라에 질의·접속하여 정보 확인 |
| 예시           | 외부 자산 검색 API나 기존 DNS 관측 정보 조회 | DNS 질의, 서비스와의 직접 통신      |
| 대상에 대한 직접 통신 | 수집 단계에서는 피할 수 있음              | 발생할 수 있음                 |
| 장점           | 대상에 주는 직접적인 부하가 적음            | 현재 상태를 확인할 기회가 늘어남       |
| 한계           | 오래되거나 누락된 정보가 있을 수 있음         | 로그·탐지·부하가 발생할 수 있음       |

여기서 수동적 정찰은 **네트워크 통신을 전혀 하지 않는다는 뜻이 아닙니다.** 외부 정보 제공 서비스에는 요청을 보냅니다.

또한 공개 자료에서 이름을 수집한 뒤 DNS 조회로 검증한다면, 전체 작업을 단순히 “수동적 수집만 했다”고 표현해서는 안 됩니다. 실제 통신 방식은 버전과 설정을 확인해야 합니다.

**5. 외부 데이터 소스의 역할**

Amass는 외부 서비스에서 제공하는 정보를 활용해 조사 결과를 보강할 수 있습니다. 공식 설정 문서는 `datasources.yaml`에서 데이터 소스와 자격 증명을 설정하는 방법을 설명하며, Shodan과 CIRCL 등을 예시로 제시합니다.

일부 데이터 소스는 API 키나 유료 구독이 필요합니다. 따라서 **동일한 도메인을 입력하더라도 사용하는 데이터 소스와 계정 권한에 따라 결과가 달라질 수 있습니다.** [데이터 소스 설정 문서](https://owasp-amass.github.io/docs/configuration/data_sources/)

결과가 적게 나왔다면 다음을 구분해서 확인해야 합니다.

* 실제로 공개된 자산이 적은 경우
* 필요한 데이터 소스가 비활성화된 경우
* API 인증이나 호출 제한에 걸린 경우
* 조사 범위나 수집 설정이 제한적인 경우

API 키와 비밀번호가 들어 있는 설정 파일은 공개 저장소에 올리지 않도록 주의해야 합니다.

**6. 결과를 어떻게 해석하는가?**

아래는 **실제 Amass 출력이 아니라 관계를 설명하기 위한 가상 예시**입니다.

| 발견한 관계                                    | 해석할 수 있는 내용                | 단정하면 안 되는 내용             |
| ----------------------------------------- | -------------------------- | ------------------------ |
| `api.example.com`의 A 레코드가 `192.0.2.10`    | 관측 시점에 이름이 해당 IPv4 주소를 가리킴 | 해당 IP의 모든 서비스가 같은 조직 소유임 |
| `shop.example.com`이 외부 서비스 이름을 CNAME으로 참조 | 외부 서비스에 의존하는 구성일 수 있음      | 외부 서비스 전체가 점검 허가 범위에 포함됨 |
| 인증서에 `dev.example.com`이 포함                | 인증서에 그 이름이 기재되어 있음         | 현재도 개발 서버가 운영 중임         |
| 과거 자료에서 `old.example.com` 발견              | 과거에 관측된 이름이 존재함            | 현재도 접속 가능함               |

특히 다음 세 가지를 구분해야 합니다.

* **이름 발견**: 자료에 도메인 이름이 나타납니다.
* **DNS 확인**: 현재 질의에서 유효한 DNS 응답을 받습니다.
* **서비스 확인**: 실제 웹이나 다른 서비스가 응답합니다.

이 세 가지는 서로 다른 상태입니다. DNS가 정상이어도 웹서비스가 없을 수 있고, 서비스가 응답해도 취약점이 있다는 뜻은 아닙니다.

**7. CDN·공유 호스팅 환경에서의 주의점**

CDN이나 공유 호스팅을 사용하는 환경에서는 **도메인과 IP가 일대일로 대응하지 않을 수 있습니다.**

예를 들어 여러 도메인이 같은 IP로 연결되더라도 같은 조직 소유라고 확정할 수 없습니다. 또한 도메인의 DNS에서 얻은 IP가 실제 애플리케이션이 실행되는 원본 서버의 IP라는 보장도 없습니다.

따라서 결과를 검토할 때는 다음 원칙이 유용합니다.

* 같은 IP라는 이유만으로 자산을 같은 조직에 귀속시키지 않습니다.
* 관련 IP를 발견했다고 해당 IP 전체가 점검 허가 범위에 들어왔다고 판단하지 않습니다.
* 공개 정보, 현재 응답, 내부 자산 목록을 함께 비교합니다.
* 발견 시점과 출처를 남겨 정보의 유효성을 검토합니다.

**8. 내부 구성**

OWASP는 Amass 프레임워크의 주요 구성으로 수집 엔진, 자산 데이터베이스, Open Asset Model을 설명합니다. [OWASP 공식 소개](https://owasp.org/www-project-amass/)

| 구성 요소                 | 역할                       |
| --------------------- | ------------------------ |
| Collection Engine     | 자산 정보를 수집하고 관련 정보를 확장    |
| Asset Database        | 발견한 자산과 관계를 저장           |
| Open Asset Model(OAM) | 자산 유형·속성·관계를 일관된 형식으로 표현 |

이 구조 덕분에 단순한 주소 목록을 넘어 **“어떤 자산이 무엇과 연결되어 있는가?”**를 관리할 수 있습니다.

수집 설정에서는 정보의 재조회 주기를 제어하는 TTL과 결과 수용에 사용하는 신뢰도 기준 등을 조정할 수 있습니다. 여기서 신뢰도 점수는 **취약점의 위험도 점수와는 다른 개념**입니다. [변환 설정 문서](https://owasp-amass.github.io/docs/configuration/transformations/)

**9. 다른 도구와의 차이**

| 도구             | 주된 목적                | 답하려는 질문                     |
| -------------- | -------------------- | --------------------------- |
| **Amass**      | 외부 자산 발견과 관계 분석      | 어떤 자산이 있고, 서로 어떻게 연결되는가?    |
| **Subfinder**  | 수동적 정보원을 통한 서브도메인 발견 | 어떤 서브도메인이 공개 정보에서 발견되는가?    |
| **Nmap**       | 호스트·포트·서비스 조사        | 어떤 포트가 열려 있고 어떤 서비스가 동작하는가? |
| **Wappalyzer** | 웹 기술 식별              | 이 웹사이트는 어떤 기술로 만들어졌는가?      |

Subfinder는 수동적 서브도메인 수집에 초점을 맞추고, Nmap은 네트워크 및 서비스 조사, Wappalyzer는 웹 기술 식별에 초점을 맞춥니다. [Subfinder 공식 문서](https://docs.projectdiscovery.io/opensource/subfinder/overview), [Nmap 공식 문서](https://nmap.org/book/man.html), [Wappalyzer 공식 사이트](https://www.wappalyzer.com/)

보안 점검에서는 Amass로 자산 후보를 찾은 뒤, **소유권과 허가 범위를 확인하고**, 목적에 맞는 도구로 후속 점검을 진행할 수 있습니다.

**10. 기본 실행 예시와 버전 주의사항**

Amass 실행 파일이 설치되고 필요한 설정이 준비되어 있다면, 기본적인 도메인 열거 형식은 다음과 같습니다.

```bash
amass enum -d example.com
```

* `amass`: 프로그램 실행
* `enum`: 자산 열거 작업
* `-d example.com`: 조사할 도메인 지정

`example.com`은 설명용 자리표시자이며, 실습할 때는 소유하거나 점검을 허가받은 도메인으로 바꿉니다. 공식 시작 문서에서도 `enum -d` 형식의 실행 예시를 제공합니다. [공식 설치·실행 문서](https://owasp-amass.github.io/docs/)

**인터넷의 예제를 복사할 때는 Amass 버전을 반드시 확인해야 합니다.** 현재 공식 시작 문서는 v5 경로를 안내하지만, 이전 버전의 명령과 설정을 사용하는 자료도 있습니다. 옵션, 출력 방식, 데이터베이스 구성 등을 서로 다른 버전의 문서에서 섞어 적용하지 않는 것이 좋습니다.

**11. 활용 범위와 한계**

Amass는 다음과 같은 작업에 활용할 수 있습니다.

* 보안 점검 전 외부 노출 자산 목록 작성
* 내부 자산 목록과 외부에서 발견되는 자산 비교
* 관리 대상에서 누락된 서비스 후보 확인
* 반복 조사 결과를 활용한 자산 변화 검토
* 도메인·인프라·외부 서비스의 의존 관계 분석

다만 **Amass의 발견 결과만으로 취약점, 서비스 용도, 소유권을 확정할 수는 없습니다.** 공개 정보의 누락과 시간 차이가 있고, 내부 전용 자산은 외부 조사로 발견하지 못할 수 있습니다.

학습할 때는 **“Amass는 점검해야 할 자산과 그 관계를 찾는 데 쓰이고, 취약 여부는 후속 검증으로 판단한다”**는 역할 구분을 기억하면 됩니다.
