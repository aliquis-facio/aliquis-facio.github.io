|구분|샤딩 (Sharding)|파티셔닝 (Partitioning)|
|---|---|---|
|**개념**|데이터를 **여러 대의 독립된 데이터베이스 서버**에 나누어 저장하는 방식|하나의 데이터베이스 내에서 **여러 개의 테이블**로 나누어 저장하는 방식|
|**확장성**|**수평적 확장(Scale-Out)**이 가능하여 서버를 계속 추가할 수 있음|단일 서버의 성능 한계 내에서만 확장 가능 (**Scale-Up** 중심)|
|**관리 복잡도**|복잡함 (애플리케이션에서 어떤 서버로 갈지 라우팅을 구현해야 함)|비교적 단순함 (DBMS가 자체적으로 분할을 관리함)|
|**목적**|트래픽 분산, 서버 부하 분산, 하드웨어 한계 극복|관리 편의성 증대, 특정 데이터 검색 시 I/O 성능 향상|
|**장애 영향**|하나의 서버가 중단되어도 다른 서버의 데이터는 안전함|서버 자체가 다운되면 모든 파티션의 데이터에 접근 불가능|

**핫 파티션(Hot Partition)**: 데이터가 특정 파티션에만 과도하게 몰려 해당 파티션을 처리하는 서버나 디스크에 부하가 집중되는 현상

샤딩이나 파티셔닝 시스템에서 전체적인 리소스는 넉넉하더라도, 단 하나의 파티션(서버)이 병목 구간이 되어 시스템 전체의 성능 저하나 장애를 유발하는 대표적인 데이터 분산 불균형 문제입니다.

#### 핫 파티션이 발생하는 주된 이유

핫 파티션은 주로 파티션 키(Partition Key / Sharding Key)를 잘못 선정했을 때 발생합니다.

- 특정 값의 빈도가 너무 높은 경우 (Data Skew):
    - 예를 들어 유저의 '거주 국가'를 키로 잡았는데, 서비스 이용자의 90%가 한국인이라면 한국 파티션에만 데이터와 트래픽이 몰리게 됩니다.
- 시간이나 순차적인 값을 키로 사용한 경우:
    - `등록_일자`나 `순차 ID(Auto Increment)`를 키로 삼으면, 현재 새로 유입되는 모든 실시간 트래픽과 최신 데이터가 가장 마지막에 생성된 파티션 하나로만 집중됩니다.
- 유명인/셀럽 효과 (Celebrity Effect):
    - SNS 서비스에서 '사용자 ID'를 키로 나누었더라도, 팔로워가 수천만 명인 인플루언서의 파티션은 다른 일반 유저의 파티션보다 압도적인 조회/댓글 트래픽을 감당해야 합니다.

#### 핫 파티션을 해결하는 핵심 전략

핫 파티션을 해결하려면 데이터를 최대한 균등하게 찢거나 부하를 분산시켜야 합니다.

1. 솔트(Salt) 추가하기 (Salting)
    - 기존의 파티션 키 뒤에 무작위 숫자나 해시값(예: `Key_0`, `Key_1`, `Key_2`)을 붙여 데이터를 여러 파티션으로 강제 분산시키는 방법입니다.
    - _단점:_ 데이터를 읽을 때 분산된 파티션들을 모두 조회해야 할 수 있으므로, 주로 쓰기 작업이 엄청나게 몰리는 테이블에 유용합니다.
2. 복합 키(Composite Key) 사용
    - 하나의 값만 키로 쓰지 않고, 두 개 이상의 컬럼을 조합하여 새로운 키를 만듭니다. (예: `유저 ID` + `주문 날짜`) 이를 통해 단일 키로 뭉치던 데이터를 더 잘게 쪼갤 수 있습니다.
3. 애플리케이션 레이어에 캐시(Cache) 도입
    - 자주 조회되는 핫 데이터(예: 인플루언서의 프로필, 실시간 인기 게시글)는 데이터베이스까지 가지 않도록 [Redis](https://redis.io/)나 [Memcached](https://memcached.org/) 같은 인메모리 캐시 서버에 저장해 둡니다. 데이터베이스 파티션으로 향하는 읽기 트래픽을 극적으로 줄일 수 있습니다.
4. 분산 해시(Consistent Hashing) 사용
    - 데이터베이스 서버(샤드)의 추가/제거가 일어날 때 데이터 재배치를 최소화하면서도, 해시 알고리즘을 통해 데이터를 전 서버에 골고루 분산시킵니다.

### AWS IAM과 접근 권한

정책: 어떤 서비스 기능에 어떤 조작을 할 수 있는지 정의

- IAM 사용자, 그룹 및 IAM 역할, AWS 리소스에 정책을 연결
- json 형식의 정책문서:
	- 필수: `Effect`, `Action`, `Resource`
- 관리형 정책: 재사용 가능
	- AWS 관리형 정책: AWS 제공 → 사용 편함
	- 고객 관리형 정책 → 고객이 직접 생성 → 세밀한 권한 설정 가능
- inline 정책: 싱글 identity (IAM 사용자, 그룹, 역할)에 연결 (policy:identity = 1:1)

다단계 인증: 종류를 따지지 않고 2번 이상 인증한다.
다요소 인증: 두 종류 이상의 인증을 사용한다.

정책 평가 우선순위

IAM 사용자
- AWS 계정 내에서 만들어진 사용자
- 개별 사용자는 고유한 자격증명을 소유
- 부여된 권한의 범위 내에서만 AWS 작업 가능
	- IAM 사용자의 업무 역할에 따라 권한을 부여

IAM 그룹
- 권한을 그룹에 연결하면 그룹 내 사용자들에게 상속의 방식으로 부여
- IAM 사용자는 여러 그룹의 멤버 가능

### 권한 경계(Permission Boundary)

- NLB(Network-)

## DAS(Direct Attached Storage)

PC와 서버에 다이렉틀 꽂아서 사용하는 스토리지
서버와 하드웨어를 1:1로 연결
하드를 여러 개 끼울 수 있는 서버의 외장하드
서버에 직접 외장저장장치를 연결 → 속도 빠르고 확장 쉬움, 연결 수에 한계

## NAS(Network Attached Storage)

서버와 저장장치가 이더넷 등의 LAN 방식의 네트워크에 연결된 방식
LAN은 TCP/IP 프로토콜 기반이고 저장장치는 SCSI를 사용 → 통신 위해 중계역할을 하는 파일서버가 필요함.
스토리지 내에서 직접 파일을 읽기/쓰기/공유

SCSI(Small Computer System Interface): 컴퓨터 주변기기 접속을 위한 직렬 표준 인터페이스

장점: PORT 수 제한이 없어 확장성과 유연성이 뛰어남, 경제적 유리, 설치 및 유지보수 용이
단점: 접속증가 시 성능저하, DAS보다 전송속도 느림, 파일시스템 공유 → 보안 비교적 취약, 백업이 어려움
