# 생성형 AI와 보안

## 1. 핵심 개념

보안 업무의 가장 큰 문제는 **정보 부족이 아니라 정보 과잉**이다. 보안 담당자는 매일 다음과 같은 대량의 정보를 처리해야 한다.

- 수백 건의 보안 경보
- 길고 복잡한 로그
- 난독화된 스크립트
- 신규 취약점 및 위협 정보
- 클라우드·Kubernetes 설정
- 보안 정책, 점검 결과, 사고 보고서

생성형 AI는 이러한 정보를 직접 최종 판단하는 것이 아니라 **사람이 판단하기 좋은 형태로 정리하고 분석을 보조하는 역할**에 적합하다.

> → AI는 **증거를 정리하고 선택지를 제안**하며, 사람은 **원본을 검증하고 최종 결정**한다.

# 2. SOC와 생성형 AI

## SOC(Security Operations Center)

**보안관제센터**로, 조직의 시스템과 네트워크를 지속적으로 감시하면서 보안 위협을 탐지하고 대응하는 조직이다.

주요 업무는 다음과 같다.

|업무|내용|
|---|---|
|모니터링|서버, PC, 네트워크, 클라우드의 로그·보안 경보 확인|
|분석|실제 공격인지 오탐인지 판단하고 피해 범위 조사|
|대응|장비 격리, 계정 차단, 사고 보고서 작성|

SOC 분석가는 하루에 수많은 경보를 분석하기 때문에 **경보 요약, 분류, 우선순위 설정** 같은 반복 업무에서 생성형 AI를 활용할 수 있다.

# 3. 생성형 AI의 보안 활용 사례

## 사례 1. 보안 경보와 로그 → 사고 타임라인

여러 보안 제품에서 발생한 로그와 경보를 AI가 하나의 **Incident Timeline**으로 정리한다.

### AI에게 맡길 수 있는 작업

- 최초 탐지 시각
- 관련 사용자·장비
- 의심 IP·도메인·파일 해시
- 실행된 프로세스·명령
- 초기 침투 → 권한 상승 → 내부 이동 등의 공격 단계
- 아직 분석되지 않은 증거
- 추가 확인 항목

### 사람이 확인해야 하는 것

AI가 만든 타임라인 자체를 증거로 간주해서는 안 된다.

최종 보고서에는 반드시 다음과 같은 **원본 증거**가 필요하다.

```
SIEM Event ID
Timestamp
Query
Original Log
```

또한 **사실과 추정**을 구분해야 한다.

# 4. 사례 2. 보안 경보 우선순위 결정

단순한 보안 제품의 심각도뿐만 아니라 **조직의 환경과 자산 중요도**를 AI가 함께 분석한다.

### 입력 정보

```
탐지 규칙
+
자산 중요도
+
인터넷 노출 여부
+
사용자 권한
+
최근 변경 사항
+
과거 경보
```

### AI 출력

예를 들어

```
긴급
높음
보통
낮음
```

과 같은 잠정 우선순위를 결정하고 판단 이유를 설명한다.

추가로

- 필요한 SIEM/EDR 조회
- 사용자 확인
- 격리 검토
- 추가 분석

등을 제안할 수 있다.

하지만 AI가 **낮은 위험**이라고 판단했다고 해서 자동으로 경보를 종료하면 안 된다.

특히 다음과 같은 중요 자산은 추가 검증이 필요하다.

- 관리자 계정
- Domain Controller
- CI/CD 자격증명
- 외부 노출 시스템

# 5. 사례 3. 위협정보에서 IOC와 TTP 추출

보안 권고문이나 Threat Intelligence 보고서를 AI가 분석하여 공격 정보를 구조화할 수 있다.

### AI 활용

- 공격자의 목적 요약
- 주요 TTP 추출
- IOC 추출
- MITRE ATT&CK 매핑
- 영향을 받는 제품·버전 정리
- 탐지 및 완화 방법 초안 생성

## TTP

**Tactics, Techniques, and Procedures**

공격자가 **어떤 방식으로 공격하는지**를 나타낸다.

### Tactics — 전술

공격자의 목적 또는 공격 단계.

예:

```
초기 침투
→
권한 상승
→
내부 이동
→
정보 유출
```

### Techniques — 기법

목적을 달성하는 방법.

예:

- 피싱 메일
- 계정 탈취
- PowerShell 실행

### Procedures — 절차

실제 공격자가 해당 기법을 구현한 구체적인 방식.

## IOC

**Indicator of Compromise — 침해지표**

공격이 발생했거나 진행되고 있음을 보여주는 **구체적인 흔적**이다.

대표적인 IOC:

- IP 주소
- 도메인
- URL
- 파일 Hash
- 이메일 주소
- 이메일 제목
- 파일명
- Registry Key

예를 들어 위협정보에서 특정 악성 IP가 공개되면 기업의 로그와 비교하여 동일한 IP와 통신했는지 확인할 수 있다.

### IOC와 TTP 차이

|구분|IOC|TTP|
|---|---|---|
|의미|공격의 흔적|공격자의 행동 방식|
|예|IP, Hash, URL|피싱, PowerShell 실행|
|변경 용이성|쉽게 변경|상대적으로 변경 어려움|
|활용|빠른 탐지·차단|변형 공격 탐지|

따라서 실무에서는

```
IOC → 빠른 탐지·차단
TTP → 공격 행동 패턴 탐지
```

를 병행한다.

# 6. 사례 4. 자연어 → 보안 헌팅 쿼리

분석가가 자연어로 원하는 탐지 조건을 입력하면 AI가 쿼리 초안을 생성할 수 있다.

예:

> 최근 24시간 동안 Office 프로세스가 PowerShell을 실행한 사례를 찾아라.

이를 다음과 같은 언어로 변환할 수 있다.

- KQL
- SPL
- SQL
- EDR Query

다만 사람이 반드시 다음을 확인해야 한다.

- 실제 필드 이름이 맞는가?
- 데이터 스키마와 맞는가?
- 원본 이벤트와 결과가 일치하는가?
- 오탐 제외 조건 때문에 공격이 누락되지 않는가?
- 미탐은 없는가?

## KQL

**Kusto Query Language**

보안 로그와 이벤트 데이터를 검색·분석하기 위한 쿼리 언어이다.

주로 다음에서 사용된다.

```
Microsoft Sentinel
Microsoft Defender
```

활용 분야:

- SIEM
- Threat Hunting
- 침해사고 분석
- 이상행위 탐지

## SPL

**Search Processing Language**

Splunk에서 사용하는 로그 검색·분석 언어이다.

주요 활용:

- 로그 분석
- 보안 이벤트 탐지
- Threat Hunting
- 침해사고 분석

# 7. 사례 5. 의심 스크립트 분석

생성형 AI는 난독화된 스크립트를 사람이 이해하기 쉽게 설명하는 데 활용할 수 있다.

### AI가 분석할 수 있는 내용

- Base64 인코딩
- URL 인코딩
- PowerShell 실행 인자
- 파일 다운로드 과정
- 파일 실행 과정
- 네트워크 통신 대상
- 지속성 확보 기법
- 조사할 파일·Registry·Process

하지만 중요한 원칙은

> **AI가 안전하다고 판단한 코드도 신뢰하지 않는다.**

실제 실행은 반드시 **격리된 Sandbox**에서 수행해야 한다.

또한 다음 데이터는 공개형 AI에 입력하지 않는 것이 원칙이다.

- 악성코드 샘플
- 고객 개인정보
- 민감 로그
- 회사 기밀

필요한 경우

```
비식별화
가명처리
마스킹
```

등을 적용한다.

# 8. 사례 6. Sigma 탐지 규칙 생성

## Sigma

특정 SIEM 제품에 종속되지 않도록 만들어진 **오픈 표준 탐지 규칙 형식**이다.

하나의 Sigma 규칙을 기반으로 여러 보안 플랫폼용 탐지 규칙을 만들 수 있다.

예:

```
Sigma Rule
      ↓
 ┌────┼─────┬──────┐
 ↓    ↓     ↓      ↓
Splunk Sentinel Elastic QRadar
```

가장 큰 장점은 **탐지 규칙의 재사용성과 이식성**이다.

### 생성형 AI 활용

보안 분석 문장을 Sigma Rule 초안으로 변환할 수 있다.

AI가 지원할 수 있는 작업:

- 탐지 조건 → Sigma 규칙
- MITRE ATT&CK 매핑
- 탐지 근거 주석
- 예상 오탐 사례
- 필요한 로그 소스
- 감사 정책

하지만 사람이 다음을 검증해야 한다.

- 필요한 로그가 실제 수집되는가?
- SIEM 필드와 일치하는가?
- 대소문자·공백 같은 예외를 처리하는가?
- 문자열 하나만으로 탐지하여 쉽게 우회되지 않는가?
- 정상 프로그램과 충돌하지 않는가?

# 9. 사례 7. 취약점 우선순위 분석

단순히 **CVSS 점수만으로 취약점 대응 우선순위를 결정하지 않고**, 실제 공격 가능성과 조직 환경을 함께 고려한다.

AI가 분석할 정보:

- CVE 설명
- CVSS Vector
- CISA KEV 포함 여부
- Vendor Advisory
- Patch Version
- 설치 버전
- SBOM
- 인터넷 노출 여부
- 공격 전제조건
- WAF 등 보완 통제

이를 바탕으로 패치 우선순위를 제안할 수 있다.

하지만 생성형 AI에는 **Hallucination(환각)** 문제가 있기 때문에

> 존재하지 않는 패치 버전이나 명령을 생성할 수 있다.

따라서 최종 패치 작업은 반드시 공급사 공식 문서로 검증해야 한다.

# 10. 사례 8. 클라우드·Kubernetes 보안 설정 분석

생성형 AI를 이용해 다음과 같은 **Misconfiguration 후보**를 탐색할 수 있다.

### IAM

- 과도한 Wildcard 권한

### Kubernetes RBAC

- 과도한 권한

### Network

- 공개 Storage
- 광범위한 Inbound Rule

### Container / Pod

- `privileged`
- `hostNetwork`
- `hostPID`
- `hostPath`

### Kubernetes Security

- `securityContext` 누락
- `NetworkPolicy` 부재

### Secret

- 비밀번호·Token 등의 평문 하드코딩

**출처:** 슬라이드 23

그러나 AI가 생성한 수정사항을 바로

```
kubectl apply
```

하거나 Terraform 코드에 적용해서는 안 된다.

다음과 같은 절차가 필요하다.

```
AI 수정안
   ↓
Schema Validation
   ↓
Policy Engine
   ↓
Test Environment
   ↓
Code Review
   ↓
Production
```

기준으로 삼아야 하는 것은 **Kubernetes 공식 문서와 Pod Security Standards**이다.

# 11. 사례 9. 피싱 메일 분석

AI가 피싱 신고 메일의 반복적인 확인 작업을 구조화할 수 있다.

확인 항목:

- 표시 이름과 실제 발신주소
- Reply-To 불일치
- SPF
- DKIM
- DMARC
- URL
- Redirect Chain
- 첨부파일 형식
- 파일 Hash
- 링크 클릭 여부
- 이후 로그인 활동
- 세션 활동
- 동일 발신자의 조직 내 수신자

CTI(Cyber Threat Intelligence) 정보와 연계하는 것도 가능하다.

단, 메일에는 개인정보와 기업 기밀이 존재할 수 있으므로 외부 AI 서비스를 사용하기 전에 데이터 정책을 확인해야 한다.

# 12. 사례 10. 침해사고 보고서 작성

생성형 AI는 확인된 증거를 기반으로 **Incident Report 초안**을 작성할 수 있다.

포함 가능한 내용:

- 사고 개요
- 타임라인
- 영향받은 시스템
- 영향받은 계정
- 침해 범위
- 격리·차단·복구 조치
- 잔여 위험
- 경영진 요약
- 재발 방지 대책

이때 입력 데이터를

```
사실(Fact)
추정(Assumption)
결정(Decision)
실행 결과(Result)
```

로 구분하는 것이 중요하다.

증거가 없는 결론은 **검증 필요**로 표시해야 한다.

# 13. 사례 11. 보안 정책 및 감사 대응

생성형 AI는 보안 정책·컴플라이언스 업무에도 활용할 수 있다.

AI가 지원할 수 있는 작업:

- 여러 정책 문서 비교
- 중복 정책 탐색
- 정책 충돌 탐색
- 통제 항목과 증적 매핑
- 인터뷰 질문 생성
- 점검표 생성
- 기술 내용을 비기술 담당자용 문장으로 변환
- 미비점 분석

대상 예:

```
ISMS
ISO 27001
```

하지만 AI가 규정 충족 여부를 **최종 판정해서는 안 된다.**

# 14. 생성형 AI 보안 도입 원칙

## 자동화는 저위험 작업부터 시작

처음부터 AI에게 시스템 제어 권한을 제공하는 것이 아니라

```
읽기
↓
요약
↓
분석
↓
추천
↓
제한적 자동화
```

순서로 확대하는 것이 바람직하다.

특히 다음은 사람 승인이 필요한 고위험 작업이다.

- 계정 비활성화
- 권한 회수
- Endpoint 격리
- Firewall 차단
- Kubernetes 리소스 삭제
- Cloud IAM 변경
- 외부 기관 통지
- 고객 통지

# 15. AI에 입력하면 안 되는 데이터 관리

생성형 AI를 도입하기 전에 **어떤 데이터를 AI에 입력할 수 있는지**부터 결정해야 한다.

AI 공급사에 확인할 사항:

|확인 항목|핵심 질문|
|---|---|
|학습|입력 데이터가 모델 학습에 사용되는가?|
|보관|Prompt와 Response는 얼마나 보관하는가?|
|위치|데이터는 어느 지역에서 처리되는가?|
|접근|공급사 직원이 대화를 볼 수 있는가?|
|삭제|데이터 삭제 기능이 있는가?|
|감사|Audit Log가 제공되는가?|
|Agent|Plugin·Agent는 어떤 권한을 가지는가?|

# 16. 생성형 AI의 가장 큰 보안 위험 — 그럴듯한 오답

보안 분야에서 가장 위험한 문제 중 하나는 **Hallucination**이다.

단순히 틀린 답보다 **그럴듯하게 틀린 답**이 더 위험하다.

따라서 다음을 확인해야 한다.

### 정확성

- 원본 로그에 없는 이벤트를 생성하지 않았는가?
- 존재하지 않는 CVE를 만들지 않았는가?
- 존재하지 않는 Patch Version을 만들지 않았는가?
- IOC와 공격기법에 출처가 있는가?
- 사실과 추정을 구분했는가?
- 시간대와 이벤트 순서가 정확한가?

### 실행 안전성

- 쿼리가 실제 스키마에서 실행되는가?
- 제안된 조치가 서비스 중단을 일으키지 않는가?
- 삭제·격리·차단에 사람 승인이 있는가?

### 감사 가능성

```
AI Input
AI Output
AI Recommendation
Human Approval
Execution Result
```

을 감사 로그로 기록하는 것이 중요하다.

# 17. 생성형 AI 보안 업무 도입 방법

처음에는 **되돌리기 쉬운 업무**를 파일럿 대상으로 선정하는 것이 좋다.

대표적인 예가 **보안 경보 요약**이다.

### 파일럿 진행 절차

```
1. 반복 업무 하나 선정
        ↓
2. AI에 입력할 수 있는 데이터 등급 정의
        ↓
3. 정답이 존재하는 과거 사례 20~50개 준비
        ↓
4. 정확도·누락·환각·시간 감소 측정
        ↓
5. Human Approval 지점 정의
        ↓
6. Prompt와 결과 Audit Logging
        ↓
7. 품질 기준 통과
        ↓
8. 다음 업무로 확대
```

# 18. 평가 지표

보안 업무에 생성형 AI를 도입했다면 단순히 "편해졌다"가 아니라 정량적으로 평가해야 한다.

### 주요 지표

|지표|의미|
|---|---|
|분석 시간 감소율|AI 도입 후 분석시간 감소 정도|
|중요 증거 누락률|AI가 핵심 로그·증거를 놓친 비율|
|잘못된 IOC·CVE 생성률|환각 발생 정도|
|Query 실행 성공률|AI가 만든 쿼리의 실제 실행 가능성|
|분석가 수정 비율|AI 결과를 사람이 얼마나 수정했는지|
|오탐·미탐 변화|탐지 성능 변화|
|승인 준수율|고위험 작업의 Human Approval 준수 여부|

```
                 생성형 AI
                     │
         ┌───────────┼───────────┐
         │           │           │
      정보 정리    분석 보조    초안 생성
         │           │           │
      로그 요약    IOC/TTP     KQL/SPL
      Timeline     CVE 분석     Sigma
      Report       Cloud 설정   보고서
         │           │           │
         └───────────┼───────────┘
                     ↓
                 사람 검증
                     ↓
              Human Approval
                     ↓
                 실제 실행
```

결국 보안에서 생성형 AI의 적합한 역할은 **Copilot**에 가깝다.

> **AI:** 읽기 → 요약 → 분석 → 비교 → 추천 → 초안 작성  
> **사람:** 원본 증거 확인 → 위험 판단 → 승인 → 실행 → 책임

특히 **격리·차단·삭제·권한 변경·패치 적용**과 같이 실제 시스템에 영향을 미치는 작업에는 **Human-in-the-loop**가 유지되어야 한다.
