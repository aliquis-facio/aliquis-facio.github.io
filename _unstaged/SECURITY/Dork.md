# Dork란?

**Dork는 검색엔진의 고급 검색 연산자를 조합한 검색식**을 뜻하며, 이러한 검색식으로 정보를 찾는 활동을 **Dorking**이라고 한다. 보안 분야에서는 주로 외부에 공개되거나 실수로 노출된 정보를 찾아내는 데 활용한다.

예를 들어 일반 검색과 Dork 검색은 다음과 같이 다르다.

```text
일반 검색
보안 가이드 PDF

Dork 검색
site:example.com filetype:pdf "보안 가이드"
```

두 번째 검색은 다음 조건으로 범위를 좁힌다.

* `example.com` 도메인에 속하는 자료
* PDF 형식의 파일
* `"보안 가이드"`라는 문구를 포함하는 자료

즉, **무작정 검색하는 것이 아니라 검색 범위·파일 형식·문구·위치를 지정하는 정밀 검색**이다.

---

## 1. Dorking과 Google Hacking

관련 용어를 구분하면 다음과 같다.

| 용어             | 의미                                              |
| -------------- | ----------------------------------------------- |
| Dork           | 특정 정보를 찾기 위해 작성한 검색식                            |
| Dorking        | Dork를 이용해 정보를 검색하는 활동                           |
| Google Dorking | Google 검색을 이용한 Dorking                          |
| Google Hacking | 보안상 의미 있는 정보를 찾는 Google Dorking을 가리키는 표현        |
| OSINT          | 공개 출처에서 정보를 수집·분석하는 활동으로, Dorking을 포함하는 더 넓은 개념 |

여기서 **Google Hacking은 Google 서버를 해킹한다는 뜻이 아니다.** Google에 이미 색인된 정보를 이용해 대상의 공개 정보나 보안상 노출을 발견한다는 의미다.

OWASP도 웹 보안 테스트의 정보수집 단계에 검색엔진을 통한 정보 노출 조사를 포함한다. [OWASP 검색엔진 기반 정보수집 가이드](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/01-Information_Gathering/01-Conduct_Search_Engine_Discovery_Reconnaissance_for_Information_Leakage)

## 2. 어떻게 정보가 검색되는가?

검색엔진의 일반적인 처리 과정은 다음과 같다.

1. **발견**: 링크나 사이트맵 등을 통해 URL을 발견한다.
2. **크롤링**: 검색봇이 페이지나 파일을 요청한다.
3. **색인**: 제목·본문·URL·파일 유형 등의 정보를 분석해 저장한다.
4. **검색**: 사용자의 검색 조건과 관련 있는 결과를 보여준다.

Dorking은 이 중 **이미 만들어진 색인을 정밀하게 조회하는 단계**에 해당한다.

예를 들어 관리자가 업무용 PDF를 공개 웹 디렉터리에 올렸다고 가정하자.

```text
https://example.com/documents/internal-guide.pdf
```

이 파일에 인증이 없고 검색엔진이 발견해 색인했다면, 다음과 같은 검색으로 나타날 수 있다.

```text
site:example.com filetype:pdf
```

핵심 원인은 Dork 자체가 아니라 **파일의 공개 배치와 접근통제 부재**다. Dork는 그 노출을 발견하기 쉽게 만들 뿐이다.

> 검색엔진에 색인되었다는 사실과 공개해도 되는 자료라는 사실은 다르다.

## 3. 주요 검색 연산자

### 3.1 기본 연산자

| 연산자         | 의미                | 예시                   |
| ----------- | ----------------- | -------------------- |
| `site:`     | 특정 도메인·URL 범위로 제한 | `site:example.com`   |
| `filetype:` | 특정 파일 유형으로 제한     | `filetype:pdf`       |
| `"문구"`      | 정확한 단어나 문구 검색     | `"보안 가이드"`           |
| `-`         | 특정 검색어 제외         | `보안 -채용`             |
| `OR`        | 여러 조건 중 하나를 만족    | `"보안" OR "security"` |
| `before:`   | 지정 날짜 이전 자료 검색    | `before:2026-01-01`  |
| `after:`    | 지정 날짜 이후 자료 검색    | `after:2026-01-01`   |

`site:`, `filetype:`, 따옴표, 제외 검색, 날짜 검색은 Google 공식 도움말에서 안내하는 기능이다. 날짜 조건은 검색엔진이 판단한 페이지 날짜를 기준으로 하므로 정확한 최초 게시일이나 파일 생성일로 해석해서는 안 된다. [Google 검색 범위 좁히기](https://support.google.com/websearch/answer/2466433?hl=ko)

### 3.2 위치 지정 연산자

| 연산자           | 검색 위치                | 예시                                  |
| ------------- | -------------------- | ----------------------------------- |
| `intitle:`    | 페이지 제목               | `intitle:"사용 설명서"`                  |
| `inurl:`      | URL                  | `inurl:docs`                        |
| `intext:`     | 페이지 본문               | `intext:"사용 설명서"`                   |
| `allintitle:` | 뒤따르는 여러 단어를 제목에서 검색  | `allintitle:network security guide` |
| `allinurl:`   | 뒤따르는 여러 단어를 URL에서 검색 | `allinurl:docs security`            |
| `allintext:`  | 뒤따르는 여러 단어를 본문에서 검색  | `allintext:network security`        |

보안 조사에서는 특히 `site:`, `inurl:`, `intitle:`을 조합해 특정 조직의 페이지와 경로를 좁혀 보는 방식이 사용된다. 다만 검색 연산자는 데이터베이스 질의처럼 완전하고 엄격한 결과를 보장하지 않는다. [OWASP 검색 연산자 설명](https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/01-Information_Gathering/01-Conduct_Search_Engine_Discovery_Reconnaissance_for_Information_Leakage)

### 3.3 `intitle:`, `inurl:`, `intext:`의 차이

다음과 같은 페이지가 있다고 가정하자.

```html
URL: https://example.com/docs/network

<title>네트워크 보안 가이드</title>

본문: 이 문서는 스위치 설정 방법을 설명합니다.
```

각 검색식이 찾는 위치는 다음과 같다.

```text
site:example.com intitle:"네트워크 보안"
→ 제목에서 찾음

site:example.com inurl:docs
→ URL에서 찾음

site:example.com intext:"스위치 설정"
→ 본문에서 찾음
```

같은 단어를 검색하더라도 **어느 위치에서 찾도록 지정하는지**에 따라 결과가 달라진다.

### 3.4 작성 시 주의사항

**콜론 뒤에 공백을 넣지 않는다.**

```text
올바른 형태
site:example.com

잘못된 형태
site: example.com
```

**여러 단어를 하나의 문구로 찾으려면 따옴표를 사용한다.**

```text
intitle:"보안 가이드"
```

**일반 문자열 검색은 정규표현식 검색이 아니다.**

`inurl:admin`은 URL에 `admin` 관련 문자열이 있는 결과를 좁혀 찾는 것이지, 관리자 페이지인지 검증하는 기능이 아니다.

**오래된 연산자 목록을 그대로 믿지 않는다.**

앞선 설명에서 `cache:`를 지원 여부 확인이 필요한 연산자로 소개했지만, 더 정확하게는 **Google의 `cache:` 연산자는 종료됐다.** Google은 2024년 9월 공식 문서에서 더 이상 작동하지 않는다고 명시했다. [Google 검색 문서 변경 기록](https://developers.google.com/search/updates)

## 4. 검색식 조합과 해석

아래 `example.com`은 설명용 도메인이다. 보안 점검 시에는 자신이 관리하거나 점검 권한을 받은 도메인으로 범위를 제한한다.

### 4.1 공개 문서 찾기

```text
site:example.com filetype:pdf
```

해석:

> 해당 도메인에서 검색엔진에 색인된 PDF 문서를 찾는다.

검색 결과에는 정상적으로 공개한 문서도 포함된다. **PDF가 검색된다는 사실만으로 정보 유출은 아니다.**

### 4.2 특정 주제의 문서 찾기

```text
site:example.com filetype:pdf "네트워크"
```

해석:

> 해당 도메인의 PDF 중 ‘네트워크’라는 단어와 관련된 자료를 찾는다.

보안 점검 외에 논문·보고서·매뉴얼 검색에도 활용할 수 있다.

### 4.3 로그인 페이지 후보 찾기

```text
site:example.com inurl:login
```

해석:

> URL에 `login`이 포함된 페이지를 찾는다.

로그인 화면 자체는 정상적인 공개 페이지일 수 있다. 확인할 것은 **로그인 페이지의 존재가 아니라 접근통제와 인증의 적절성**이다.

### 4.4 개발·테스트 경로 후보 찾기

```text
site:example.com inurl:staging
```

해석:

> URL에 `staging`이 포함된 페이지를 찾는다.

검색 결과가 실제 테스트 서버인지, 단순히 테스트 환경을 설명하는 문서인지는 별도로 확인해야 한다.

### 4.5 내부용 문구가 포함된 문서 점검

```text
site:example.com filetype:pdf "내부용"
```

해석:

> 해당 도메인의 PDF 중 ‘내부용’ 문구가 포함된 자료를 찾는다.

내부용 문구가 공개 정책 문서에 예시로 등장할 수도 있으므로, 검색 결과만으로 유출을 확정하지 않는다.

### 4.6 불필요한 결과 제외

```text
site:example.com filetype:pdf "보안" -채용 -보도자료
```

해석:

> 보안 관련 PDF를 찾되 채용·보도자료 관련 결과를 제외한다.

다만 제외 단어가 원하는 문서에도 등장하면 그 문서까지 빠질 수 있다.

### 4.7 검색 범위를 단계적으로 좁히기

처음부터 복잡한 검색식을 작성하기보다 다음처럼 조건을 추가하면 결과를 해석하기 쉽다.

```text
site:example.com
```

```text
site:example.com filetype:pdf
```

```text
site:example.com filetype:pdf "보안"
```

```text
site:example.com filetype:pdf "보안" -채용
```

이 방식은 **어떤 조건 때문에 결과가 줄어드는지** 파악하는 데 유리하다.

## 5. 보안 분야에서 무엇을 확인하는가?

Dorking으로 발견하는 것은 크게 다음과 같은 **노출 후보**다.

| 점검 대상      | 확인할 내용                     |
| ---------- | -------------------------- |
| 공개 문서      | 내부 자료·개인정보가 의도치 않게 포함됐는지   |
| 개발·테스트 페이지 | 운영 외 환경이 외부에 공개돼 있는지       |
| 관리 인터페이스   | 필요한 인증·접근 제한이 적용돼 있는지      |
| 오류 페이지     | 내부 경로·구성·기술 정보가 과도하게 노출되는지 |
| 파일 목록 페이지  | 디렉터리 내용이 의도치 않게 공개되는지      |
| 과거 페이지     | 폐기한 서비스나 자료가 검색 결과에 남았는지   |

중요한 판단은 다음 세 가지를 분리하는 것이다.

* **발견**: 검색 결과에 URL이 나타났다.
* **노출**: 공개하면 안 되는 정보에 실제로 접근할 수 있다.
* **취약점**: 보안 요구사항을 위반하는 문제가 확인됐다.

예를 들어 `/admin/`이 검색되더라도 인증과 권한 검사가 정상이라면, 그것만으로 취약점이라고 할 수 없다.

## 6. 수동적 정보수집인가?

**검색엔진에 질의하는 단계는 일반적으로 대상 시스템에 대한 수동적 정보수집에 가깝다.**

검색 요청은 대상 웹 서버가 아니라 검색엔진에 전달되기 때문이다. 그러나 이후 행동은 구분해야 한다.

| 행동              | 대상 시스템에 직접 요청하는가? |
| --------------- | ----------------- |
| 검색엔진에 Dork 입력   | 일반적으로 아니오         |
| 검색 결과의 제목·요약 확인 | 일반적으로 아니오         |
| 결과 링크 클릭        | 예                 |
| 문서 다운로드         | 예                 |
| 로그인 시도·취약점 검사   | 예                 |

따라서 **Dorking으로 시작했다고 해서 이후의 모든 행동이 수동적 조사인 것은 아니다.** 결과 페이지를 열면 대상 서버에 접속 기록이 남을 수 있다.

## 7. 다른 도구·기법과의 차이

| 도구·기법      | 핵심 질문                  | 주된 정보             |
| ---------- | ---------------------- | ----------------- |
| Dorking    | 검색엔진에 무엇이 공개돼 있는가?     | 페이지·문서·URL·노출 흔적  |
| Amass      | 어떤 도메인·하위 도메인이 존재하는가?  | 도메인과 관련 자산        |
| Wappalyzer | 이 웹사이트는 어떤 기술로 구성됐는가?  | 프레임워크·CMS·라이브러리 등 |
| Nmap       | 이 호스트에서 어떤 서비스가 동작하는가? | 포트·서비스 응답         |
| 웹 아카이브     | 과거에는 어떤 페이지가 있었는가?     | 이전 웹 페이지 기록       |

Dorking, 자산 탐색, 기술 식별은 서로 대체하는 관계보다는 **서로 다른 단서를 제공하는 관계**다.

또한 GitHub 코드 검색이나 Shodan·Censys의 검색 필터를 이용한 정밀 검색도 넓은 의미에서 Dorking이라고 부르곤 한다. 다만 **Google 검색식을 다른 플랫폼에 그대로 적용할 수 있는 것은 아니다.** 플랫폼마다 문법과 데이터 범위가 다르다.

## 8. Dorking의 한계

### 8.1 전체 자산 목록이 아니다

검색 결과는 검색엔진이 발견하고 색인한 범위에 한정된다. 따라서 `site:` 검색 결과를 조직의 전체 웹 자산 목록으로 간주하면 안 된다. Google도 검색 연산자가 색인·검색상의 제한을 받는다고 안내한다. [Google 검색 연산자 안내](https://developers.google.com/search/docs/monitor-debug/search-operators)

### 8.2 현재 상태와 다를 수 있다

삭제되거나 접근이 차단된 페이지가 검색 결과에 남아 있을 수 있다. 반대로 새로 공개한 페이지가 아직 나타나지 않을 수도 있다.

### 8.3 문자열 일치가 의미 일치를 보장하지 않는다

* `admin`이 포함됐지만 관리자 화면이 아닐 수 있다.
* `staging`이 포함됐지만 테스트 서버가 아닐 수 있다.
* `내부용`이 포함됐지만 공개 교육 자료일 수 있다.

### 8.4 보안 통제를 우회하지 않는다

Dorking 자체는 로그인이나 권한 검사를 우회하는 기술이 아니다. 색인된 URL이 보이더라도 원본에 접근하려면 인증이 필요할 수 있다.

> **검색되지 않음 ≠ 안전함**
> **검색됨 ≠ 취약함**

## 9. 노출을 방지하는 방법

### 9.1 접근통제가 우선이다

민감한 파일은 검색엔진에서 숨기는 것보다 먼저 **허가된 사용자만 접근하도록 설정**해야 한다.

* 인증과 파일별 권한 검사
* 비공개 저장소 사용
* 웹 공개 경로와 내부 파일 저장 위치 분리
* 불필요한 테스트 환경 외부 공개 차단
* 배포물에서 백업·로그·설정 파일 제외

URL을 복잡하게 만드는 것만으로 접근통제를 대신할 수 없다.

### 9.2 `robots.txt`는 접근 차단 장치가 아니다

```text
User-agent: *
Disallow: /internal/
```

이 설정은 검색봇에 `/internal/` 경로를 크롤링하지 말라고 요청한다. 사용자 접속을 막는 설정은 아니다.

또한 다른 페이지에서 URL이 발견되면, 내용을 크롤링하지 않아도 URL이 검색 결과에 나타날 수 있다. Google은 `robots.txt`를 검색 결과에서 페이지를 숨기는 수단으로 사용하지 말라고 안내한다. [Google robots.txt 소개](https://developers.google.com/search/docs/crawling-indexing/robots/intro)

### 9.3 `noindex`는 색인 제외용이다

HTML 페이지:

```html
<meta name="robots" content="noindex">
```

HTTP 응답 헤더:

```http
X-Robots-Tag: noindex
```

PDF 같은 비HTML 파일에는 HTTP 헤더 방식을 적용할 수 있다.

주의할 점은 **검색봇이 해당 응답을 읽어야 `noindex`를 확인할 수 있다는 것**이다. `robots.txt`로 크롤링을 막으면 `noindex`를 읽지 못할 수 있다. 그렇다고 민감한 파일을 검색봇에 보여주기 위해 인증을 해제해서는 안 된다. 민감정보는 접근통제가 우선이다. [Google noindex 안내](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

### 9.4 세 가지 통제를 구분한다

| 설정           | 목적                 | 사용자 접근 차단 |
| ------------ | ------------------ | --------- |
| 인증·권한 검사     | 허가된 사용자에게만 제공      | 가능        |
| `robots.txt` | 협조적인 봇의 크롤링 제어     | 불가능       |
| `noindex`    | 검색 결과에 색인하지 않도록 요청 | 불가능       |

이 차이를 이해하는 것이 Dorking 방어의 핵심이다.

### 9.5 이미 노출됐다면

1. 원본 자료의 접근을 차단하거나 공개 위치에서 제거한다.
2. 비밀번호·토큰 등이 포함됐다면 즉시 폐기·교체한다.
3. 접근 로그를 확인해 노출 범위를 조사한다.
4. 검색엔진의 삭제 도구로 검색 결과 제거를 요청한다.
5. 재배포나 재색인이 발생하지 않도록 원인을 수정한다.

**검색 결과를 지우는 것과 실제 유출 위험을 제거하는 것은 별개**다.

## 10. 점검할 때의 원칙

검색식 작성과 결과 확인은 허가된 범위에서 진행하고, 발견한 정보를 불필요하게 수집하지 않는다.

특히 다음은 구분해야 한다.

* 검색 결과에서 계정정보가 보이는 것과 그 계정으로 로그인하는 것
* 파일 주소를 발견하는 것과 민감정보를 대량 다운로드하는 것
* 서비스 이름을 확인하는 것과 취약점을 직접 시험하는 것

검색 결과에 나타났다는 사실은 추가 접근이나 이용에 대한 허가를 뜻하지 않는다.

## 핵심 요약

**Dork는 정밀 검색식이고, Dorking은 그 검색식으로 공개 정보를 찾는 활동이다.**

학습할 때는 다음 순서로 기억하면 된다.

1. `site:`로 **어디에서** 찾을지 정한다.
2. `filetype:`으로 **어떤 자료를** 찾을지 정한다.
3. `intitle:`, `inurl:`, `intext:`로 **어느 위치에서** 찾을지 정한다.
4. 따옴표·제외·날짜 조건으로 결과를 좁힌다.
5. 검색 결과를 **노출 후보**로 해석하고 실제 보안 문제와 구분한다.

방어 관점에서 가장 중요한 문장은 다음과 같다.

> **검색엔진에서 숨기는 것은 접근통제를 대신하지 않는다.**
