# 1. 소프트웨어 전공 학생 관점

## <font color="#ff0000">Q1. 정적 분석이란 무엇인가요?</font>

<font color="#ff0000">정적 분석은 파일을 직접 실행하지 않고 파일 자체의 구조와 내용을 검사하는 방식입니다.</font> 본 프로젝트에서는 파일명, 확장자, Magic Bytes, MIME 타입, 바이트 분포, 문자열, 압축 구조 등을 분석했습니다.

<font color="#ff0000">파일을 실행하지 않기 때문에 분석 환경에서 악성코드가 동작할 위험이 낮고, 업로드 시점에 빠르게 적용할 수 있다</font>는 장점이 있습니다.

---

## Q2. 동적 분석 대신 정적 분석을 선택한 이유는 무엇인가요?

파일 업로드 서비스에서는 사용자가 파일을 제출한 직후 빠르게 위험도를 판단해야 합니다. 동적 분석은 샌드박스에서 파일을 실행해야 하므로 분석 시간이 길고 별도 격리 환경이 필요합니다.

반면 정적 분석은 파일을 실행하지 않고 특징을 추출하므로 상대적으로 빠르고 안전합니다. 따라서 1차 필터링 단계에 적합하다고 판단했습니다.

다만 실행 중에만 나타나는 네트워크 연결, 프로세스 생성, 파일 변조 같은 행위는 확인하기 어렵기 때문에 정적 분석만으로 모든 공격을 탐지할 수는 없습니다.

---

## Q3. 전체 처리 과정은 어떻게 구성되어 있나요?

전체 과정은 다음과 같습니다.

1. 분석 대상 파일과 하위 디렉터리 탐색
2. 파일명·확장자·크기 정보 추출
3. Magic Bytes를 이용한 실제 형식 판별
4. 확장자·MIME 타입과 실제 형식 비교
5. 바이트 통계 및 엔트로피 계산
6. URL·IP·명령어·위험 API·난독화 문자열 탐지
7. 압축파일 내부 구조 분석
8. 결과를 38개 Feature로 변환
9. 정상 `0`, 악성·이상 `1`로 라벨링
10. CSV 또는 DataFrame 형태로 모델에 전달

---

## Q4. 파일을 직접 실행하지 않고 어떻게 악성 여부를 판단하나요?

악성 파일에서 자주 나타나는 구조적 특징을 수치화하여 판단합니다.

예를 들어 확장자는 `.jpg`지만 파일 헤더가 실행 파일 형식이면 확장자 위장 가능성이 있습니다. 파일 내부에 PowerShell, `cmd`, `eval`, `base64_decode` 등의 문자열이 반복되면 명령 실행이나 난독화 가능성을 의심할 수 있습니다.

압축파일 안에 실행 파일이나 스크립트가 포함되어 있거나 압축 해제 크기가 지나치게 크다면 악성 파일 은닉이나 압축 폭탄 가능성을 탐지할 수 있습니다.

---

## Q5. Magic Bytes가 무엇인가요?

<font color="#ff0000">Magic Bytes는 파일의 시작 부분에 기록되는 파일 형식 식별 값</font>입니다.

예를 들어 PDF는 일반적으로 `%PDF`, PNG는 정해진 PNG 시그니처, 실행 파일은 `MZ`로 시작합니다. 확장자는 사용자가 쉽게 변경할 수 있지만 Magic Bytes는 실제 파일 구조와 관련되어 있으므로 확장자 위장 탐지에 활용할 수 있습니다.

---

## Q6. 확장자와 Magic Bytes가 다르면 무조건 악성인가요?

아닙니다. 불일치는 위험 신호 중 하나일 뿐이며, 단독으로 악성이라고 판단하지 않습니다.

파일이 잘못 저장되었거나 웹 서버가 부정확한 MIME 타입을 제공한 경우에도 불일치가 발생할 수 있습니다. 따라서 Magic Bytes 불일치뿐만 아니라 의심 문자열, 내부 시그니처, 엔트로피, 압축 구조 등 여러 Feature를 함께 사용합니다.

---

## Q7. MIME 타입은 어떻게 활용했나요?

다음 세 가지 정보를 비교하는 데 활용했습니다.

* 파일 확장자가 나타내는 형식
* Magic Bytes로 판단한 실제 형식
* 외부에서 전달된 MIME 타입

예를 들어 `.png` 확장자를 사용하고 있지만 실제 헤더가 ZIP이고 MIME 타입이 `image/png`라면 형식 위장 가능성이 있습니다.

MIME 타입이 제공되지 않은 경우에는 불일치로 간주하지 않고 결측 상태로 처리하여 정상 파일에 불필요한 패널티가 발생하지 않도록 했습니다.

---

## Q8. 이중 확장자는 어떻게 탐지하나요?

파일명의 확장자 구분 기호와 확장자 패턴을 분석합니다.

예를 들어 `report.pdf.exe`, `image.jpg.php`와 같이 사용자가 앞부분의 정상 확장자만 보고 파일을 오인할 수 있는 형태를 탐지합니다.

다만 `archive.tar.gz`처럼 정상적으로 이중 확장자를 사용하는 형식도 있으므로, 이중 확장자 여부만으로 차단하지 않고 마지막 확장자의 위험도와 실제 파일 형식을 함께 확인합니다.

---

7p에서 보실 수 있듯이 크게 다섯 그룹으로 구성했습니다.

| Feature 그룹  | 주요 내용                                                          |

| 파일명·크기, 확장자 | 파일 크기, 파일명 길이, 이중 확장자, 특수문자 비율<br>실행·스크립트·압축·매크로·알 수 없는 확장자 여부 |
| 형식 검증       | Magic Bytes, MIME 불일치, 내부 시그니처                                 |

| 압축 구조       | 내부 파일 수, 실행·스크립트 수, 중첩 깊이, 압축률                                 |

## Q10. 왜 파일 내용을 그대로 모델에 넣지 않고 Feature를 추출했나요?

원본 파일은 형식과 크기가 서로 다르기 때문에 일반적인 머신러닝 모델에 바로 입력하기 어렵습니다. 또한 전체 바이트를 직접 입력하면 학습 비용이 커지고 모델의 판단 근거를 설명하기 어렵습니다.

따라서 보안상 의미가 있는 정보를 38개의 정형 Feature로 변환했습니다. 이 방식은 Random Forest와 같은 전통적인 머신러닝 모델에 적합하고, 어떤 특징이 판정에 영향을 주었는지 비교적 쉽게 해석할 수 있습니다.

---

## <font color="#ff0000">Q11. 처리할 수 없는 파일 형식은 어떻게 하나요?</font>

지원하지 않는 형식도 <font color="#245bdb">기본적인 파일명, 확장자, 크기, 바이트 통계, 문자열 분석은 수행할 수 있습니다.</font>

형식별 상세 파싱이 불가능한 경우에는 `is_unknown_extension`이나 Magic Bytes 관련 Feature에 반영합니다. 분석할 수 없다는 이유만으로 곧바로 악성으로 처리하지는 않습니다.

---

## Q12. 파일을 읽는 과정에서 오류가 발생하면 어떻게 하나요?

분석 실패 파일은 오류 로그와 함께 별도로 기록하고 전체 전처리 과정이 중단되지 않도록 예외 처리했습니다.

또한 파일이 지나치게 크거나 손상된 경우를 고려해 읽기 범위, 압축 해제 크기, 중첩 깊이 등에 제한을 두는 방식으로 서비스 거부 위험을 줄일 수 있도록 설계했습니다.

---

# 2. 데이터셋 및 전처리 관점

## <font color="#ff0000">Q13. 데이터셋은 어떻게 구성했나요?</font>

최종 데이터셋은 총 40,552개입니다.

| 구분    |    파일 수 |    비율 |
| ----- | ------: | ----: |
| 정상    | 12,781개 | 31.5% |
| 악성·이상 | 27,771개 | 68.5% |
| 합계    | 40,552개 |  100% |

총 94개의 파일 유형을 포함했으며, 정상 파일은 arXiv, NapierOne, WordPress 및 정상 오픈소스 저장소 등에서 수집했습니다. 악성 파일은 MalwareBazaar, DikeDataset, CIC-Evasive-PDFMal2022, WebShell 표본 및 자체 생성 Image Anomaly 데이터로 구성했습니다.

---

## Q14. 정상과 악성 데이터 비율이 불균형한데 문제가 없나요?

악성·이상 데이터가 약 68.5%로 더 많기 때문에 클래스 불균형이 존재합니다.

단순 정확도만 사용하면 다수 클래스에 유리한 결과가 나올 수 있으므로 Precision, Recall, F1-score와 Confusion Matrix를 함께 확인해야 합니다. 특히 보안 모델에서는 악성 파일을 정상으로 판단하는 False Negative를 중요하게 봐야 합니다.

향후에는 클래스 가중치, 언더샘플링, 계층화 분할 등을 적용해 불균형의 영향을 더 엄밀하게 검증할 필요가 있습니다.

---

## Q15. 왜 다양한 데이터셋을 합쳤나요?

하나의 데이터셋만 사용하면 특정 파일 형식이나 수집 환경에 편향될 수 있기 때문입니다.

예를 들어 MalwareBazaar는 실제 악성 파일을 제공하지만 정상 파일이 부족하고, NapierOne은 다양한 정상 형식을 제공하지만 악성 표본은 제공하지 않습니다. 여러 출처를 통합하여 정상·악성 표본과 파일 유형을 보완했습니다.

---

## Q16. 데이터셋마다 컬럼 구조가 다른데 어떻게 통합했나요?

각 데이터셋의 원본 메타데이터를 그대로 합친 것이 아니라 실제 파일을 동일한 전처리기에 입력해 공통 38개 Feature를 다시 추출했습니다.

이후 다음 항목을 통일했습니다.

* Feature 이름과 순서
* 자료형
* 확장자의 대소문자
* 라벨 표현
* 결측값 처리 방식
* 분석 실패 기록 방식

최종적으로 모든 데이터가 동일한 스키마를 사용하도록 구성했습니다.

---

## Q17. 데이터 라벨은 어떻게 통일했나요?

이진 분류 기준으로 정상 파일은 `0`, 악성 또는 이상 파일은 `1`로 통일했습니다.

기존 데이터셋에서 문자열이나 다른 숫자로 제공되던 라벨도 같은 기준으로 변환했습니다. Image Anomaly처럼 직접 생성한 공격 표본은 생성 과정과 원본·페이로드 정보를 manifest에 기록하고 악성·이상 라벨 `1`을 부여했습니다.

## Q20. 원본 파일에서 파생된 Polyglot 파일이 양쪽 세트에 들어가면 문제가 되지 않나요?

문제가 될 수 있습니다. 동일한 원본 이미지에서 생성된 변형 파일이 학습 세트와 평가 세트에 각각 포함되면 모델이 원본의 특성을 기억해 높은 성능을 보일 수 있습니다.

따라서 `source_id` 또는 `pair_id`를 기준으로 그룹을 묶고, 같은 원본에서 파생된 파일은 반드시 동일한 데이터 분할에 배치하는 Group-based Split이 필요합니다.

---

## Q21. 데이터 출처 자체를 모델이 학습할 가능성은 없나요?

가능성이 있습니다.

특정 출처의 정상 파일에는 특정 생성 도구나 메타데이터가 반복되고, 특정 악성 데이터셋에는 고유한 구조가 반복될 수 있습니다. 모델이 악성 행위보다 이러한 출처별 특징을 학습하면 새로운 환경에서 성능이 떨어질 수 있습니다.

이를 줄이기 위해 다음 개선이 필요합니다.

* 출처 단위 학습·평가 분리
* 외부 독립 데이터셋 검증
* 출처별 성능 비교
* 확장자·파일 크기 분포 균형 조정
* 메타데이터 제거 전후 성능 비교

---

## Q22. 데이터셋에서 PDF가 많으면 모델이 PDF 자체를 악성으로 판단하지 않나요?

그럴 가능성이 있습니다. 악성 PDF가 전체 데이터에서 큰 비중을 차지하면 모델이 실제 악성 구조보다 PDF 확장자를 강한 판단 기준으로 사용할 수 있습니다.

따라서 전체 성능뿐만 아니라 확장자별 정상·악성 분포와 파일 유형별 성능을 확인해야 합니다. 또한 확장자 Feature를 제외한 비교 실험을 수행하면 모델이 파일 유형에 얼마나 의존하는지 평가할 수 있습니다.

---

## Q23. 결측값은 어떻게 처리했나요?

Feature별로 의미에 맞게 처리해야 합니다.

예를 들어 MIME 타입이 제공되지 않은 것은 MIME 불일치가 발생한 것과 의미가 다릅니다. 따라서 MIME 미제공 상태를 무조건 불일치 `1`로 처리하지 않고 별도 결측 상태 또는 중립값으로 처리했습니다.

반면 탐지 결과가 없는 문자열 개수처럼 실제로 “없음”을 의미하는 Feature는 `0`으로 처리할 수 있습니다.

---

## Q24. 범주형 Feature는 어떻게 처리했나요?

`extension_category`와 같은 범주형 Feature는 모델에 입력하기 전에 숫자 형태로 변환해야 합니다.

가능한 방법은 One-Hot Encoding 또는 고정된 카테고리 매핑입니다. 이때 학습 데이터에 없던 새로운 범주가 서비스에서 입력될 수 있으므로 `UNKNOWN` 카테고리를 별도로 두어야 합니다.

---

## Q25. 데이터 전처리 과정에서 정보 누수가 발생할 가능성은 없나요?

가능성이 있습니다. 대표적인 정보 누수 사례는 다음과 같습니다.

* 라벨이나 데이터셋 이름이 Feature에 포함되는 경우
* 동일 파일이 학습·평가 세트에 동시에 포함되는 경우
* 동일 원본에서 파생된 변형 파일이 서로 다른 세트에 포함되는 경우
* 전체 데이터로 스케일링한 뒤 분할하는 경우
* 파일 경로나 이름에 출처 정보가 남아 있는 경우

따라서 분할을 먼저 수행하고, 인코딩이나 스케일링 설정은 학습 데이터만으로 결정해야 합니다.

## Q27. Random Forest를 선택한 이유는 무엇인가요?

입력 데이터가 38개의 정형 Feature로 구성되어 있어 트리 기반 모델이 적합했습니다.

Random Forest는 다음 장점이 있습니다.

* 수치형과 범주형 변환 Feature를 함께 처리하기 쉬움
* 비선형 관계를 학습할 수 있음
* Feature 간 복잡한 상호작용을 반영할 수 있음
* 이상치와 스케일에 비교적 강함
* Feature Importance를 통해 판단 근거를 분석할 수 있음
* 딥러닝보다 학습 및 추론 비용이 낮음

---

## Q28. Feature 스케일링을 적용했나요?

Random Forest와 같은 트리 기반 모델은 거리 기반 모델과 달리 Feature의 크기에 크게 영향을 받지 않기 때문에 필수적인 표준화는 필요하지 않습니다.

다만 Logistic Regression, SVM, KNN 등의 비교 모델을 사용할 경우에는 학습 데이터 기준으로 표준화해야 합니다. 이때 평가 데이터의 통계가 학습 과정에 반영되지 않도록 주의해야 합니다.

---

## Q29. 어떤 Feature가 가장 중요했나요?

정확한 중요도 순위는 모델에서 산출된 결과를 제시해야 하며 임의로 단정할 수 없습니다.

다만 구조적으로는 다음 Feature가 중요한 후보입니다.

* 확장자·MIME 불일치
* Magic Bytes 유효성
* 내부 파일 시그니처 수
* 의심 문자열 및 명령어 수
* 실행·네트워크 API 수
* 전체 및 헤더 엔트로피
* 압축 내부 실행 파일 수
* 압축률과 압축 폭탄 여부

단순 Feature Importance는 편향될 수 있으므로 Permutation Importance나 SHAP을 함께 사용하는 것이 더 적절합니다.

---

## Q30. 확장자 Feature가 모델 성능을 지나치게 높인 것은 아닌가요?

가능성을 배제할 수 없습니다. 이를 확인하려면 Ablation Study가 필요합니다.

예를 들어 다음 모델을 비교할 수 있습니다.

1. 전체 38개 Feature 사용
2. 확장자 관련 Feature 제거
3. 파일명 관련 Feature 제거
4. 파일 내용·구조 Feature만 사용
5. 데이터 출처별 독립 평가

확장자 Feature를 제거했을 때 성능이 급격하게 떨어진다면 모델이 실제 악성 구조보다 파일 유형에 크게 의존하고 있다는 의미입니다.

---

## Q31. Feature 중요도가 높으면 그 Feature가 악성의 원인이라고 볼 수 있나요?

아닙니다. Feature Importance는 모델이 분류에 많이 사용했다는 의미이지, 해당 Feature가 악성의 원인이라는 의미는 아닙니다.

예를 들어 PDF 확장자의 중요도가 높다면 악성 PDF가 데이터셋에 많이 포함되었기 때문일 수 있습니다. 따라서 Feature 중요도는 데이터 분포 및 출처 편향과 함께 해석해야 합니다.

---

## Q32. 왜 딥러닝이나 원본 바이트 기반 모델을 사용하지 않았나요?

이번 프로젝트의 목적은 업로드 파일을 빠르고 설명 가능하게 판별하는 정적 분석 파이프라인을 구축하는 것이었습니다.

원본 바이트 기반 딥러닝 모델은 파일 크기 처리, 학습 자원, 설명 가능성, 다양한 파일 형식 대응에서 추가적인 복잡성이 발생합니다. 따라서 보안 의미가 있는 38개 Feature를 추출하고 전통적인 머신러닝 모델을 적용했습니다.

향후에는 정적 Feature 모델과 바이트 기반 딥러닝 모델을 결합하는 앙상블도 고려할 수 있습니다.

---

## Q33. 모델이 처음 보는 파일 형식도 탐지할 수 있나요?

일부는 가능합니다.

알려지지 않은 확장자라도 엔트로피, 출력 가능 문자 비율, Null Byte 비율, 의심 문자열, 내부 시그니처 등의 형식 독립적인 Feature를 추출할 수 있습니다.

하지만 해당 형식의 정상·악성 구조를 충분히 학습하지 않았다면 성능이 낮아질 수 있습니다. 따라서 미지원 형식에는 낮은 신뢰도 표시, 추가 검사 또는 격리 정책을 적용하는 것이 적절합니다.

---

## Q34. 모델의 확률값을 그대로 위험도로 사용할 수 있나요?

Random Forest의 예측 확률은 실제 악성 가능성과 완전히 일치한다고 볼 수 없습니다.

서비스에서 위험 점수로 사용하려면 Calibration Curve, Brier Score 등을 이용해 확률 보정을 검증해야 합니다. 또한 차단 기준은 서비스의 위험 허용 수준에 따라 조정해야 합니다.

예를 들어 공공기관 문서 업로드 시스템은 Recall 중심으로 임계값을 낮추고, 일반 파일 공유 서비스는 오탐을 줄이기 위해 더 높은 임계값을 사용할 수 있습니다.

---

## Q35. 정확도 외에 가장 중요한 평가지표는 무엇인가요?

보안 탐지에서는 Recall과 False Negative가 특히 중요합니다.

* Precision: 악성으로 판정한 파일 중 실제 악성의 비율
* Recall: 실제 악성 파일 중 탐지한 비율
* F1-score: Precision과 Recall의 균형
* False Positive: 정상 파일을 악성으로 차단
* False Negative: 악성 파일을 정상으로 허용

서비스 목적에 따라 오탐과 미탐의 비용을 비교해 임계값을 결정해야 합니다.

# 4. 보안 전문가 관점

## Q36. 정적 분석만으로 난독화된 악성코드를 탐지할 수 있나요?

일부 난독화 특징은 탐지할 수 있지만 완전한 탐지는 어렵습니다.

본 프로젝트에서는 Base64 후보 문자열, 높은 엔트로피, `eval`, `base64_decode`, `gzinflate`, `str_rot13` 등의 난독화 관련 패턴을 탐지했습니다.

하지만 문자열을 여러 조각으로 분리하거나 실행 시점에 복호화하는 공격은 정적 문자열 탐지만으로 발견하기 어렵습니다. 이런 경우에는 디코딩·정규화 단계나 동적 분석이 추가로 필요합니다.

---

## <font color="#ff0000">Q37. 웹셸은 어떤 기준으로 탐지하나요?</font>

PHP, JSP, ASP, ASPX 등에서 자주 사용되는 명령 실행 및 입력 처리 패턴을 탐지했습니다.

예시는 다음과 같습니다.

* `system`, `exec`, `passthru`, `shell_exec`
* `popen`, `proc_open`
* `Runtime.exec`, `ProcessBuilder`
* `eval`, `assert`
* `base64_decode`, `gzinflate`
* `$_GET`, `$_POST`, `$_REQUEST`
* `Request.Form`, `Server.CreateObject`

다만 이러한 함수는 정상 코드에서도 사용될 수 있으므로 단일 문자열만으로 악성 판정을 내리지 않고 입력 수신, 난독화, 명령 실행 패턴 등의 조합을 모델이 판단하도록 구성했습니다.

---

## Q38. 정상 PHP 코드에도 `eval`이나 `exec`가 있을 수 있는데 오탐하지 않나요?

오탐 가능성이 있습니다.

위험 함수의 존재 자체가 악성을 의미하지 않기 때문에 함수 출현 횟수, 사용자 입력과의 결합, 난독화 여부, 네트워크 API, 파일 구조 등 여러 Feature를 함께 사용합니다.

향후에는 단순 문자열 개수뿐 아니라 함수 호출 관계나 사용자 입력이 실행 함수까지 전달되는지를 분석하는 데이터 흐름 분석을 추가하면 오탐을 줄일 수 있습니다.

---

## <font color="#ff0000">Q39. 문자열 탐지는 대소문자나 인코딩 우회를 어떻게 처리하나요?</font>

기본적으로 대소문자를 정규화하고 다양한 표현을 정규표현식으로 탐지할 수 있습니다.

하지만 다음과 같은 우회에는 한계가 있습니다.

* 문자열 분할
* 유니코드 이스케이프
* 문자 코드 조합
* Base64 다중 인코딩
* 압축 또는 암호화
* 동적 함수명 생성

향후에는 URL 디코딩, HTML Entity 디코딩, Base64 제한적 복호화, 유니코드 정규화 등을 단계적으로 적용할 필요가 있습니다.

---

## <font color="#ff0000">Q40. Polyglot 파일은 어떻게 탐지하나요?</font>

Polyglot 파일은 하나의 파일이 두 개 이상의 파일 형식으로 해석될 수 있도록 구성된 파일입니다.

본 프로젝트에서는 다음 정보를 활용했습니다.

* 확장자와 Magic Bytes의 불일치
* 파일 내부에 존재하는 다른 형식의 시그니처 수
* 정상 종료 지점 이후의 추가 데이터
* 비정상적인 헤더·푸터 구조
* 엔트로피 및 바이트 분포 변화

Image Anomaly 데이터셋은 Mitra를 이용해 정상 이미지와 HTML, PDF, ZIP, 텍스트, 바이너리 페이로드를 결합하여 생성했습니다.

---

## <font color="#ff0000">Q41. Mitra로 만든 데이터만으로 실제 Polyglot 공격을 대표할 수 있나요?</font>

완전히 대표할 수는 없습니다.

Mitra는 재현 가능한 다양한 Polyglot 구조를 생성하는 데 유용하지만, 생성 방식의 규칙성이 모델에 학습될 가능성이 있습니다. 실제 공격자는 수동으로 구조를 변경하거나 도구와 다른 방식을 사용할 수 있습니다.

따라서 Mitra 생성 데이터는 부족한 공격 유형을 보완하는 용도로 사용하고, 실제 Polyglot 표본과 이미지 파서 CVE 재현 파일을 추가해 외부 검증해야 합니다.

---

## <font color="#ff0000">Q42. trailing payload는 어떻게 확인하나요?</font>

파일 형식의 정상 종료 지점 뒤에 추가 데이터가 존재하는지 확인합니다.

예를 들어 JPEG의 종료 마커나 PNG의 종료 청크 뒤에 실행 코드, ZIP, HTML 등의 데이터가 추가될 수 있습니다. 이러한 후행 데이터는 정상 뷰어에서 무시될 수 있지만 다른 처리 과정에서는 해석될 가능성이 있습니다.

다만 일부 정상 프로그램도 메타데이터나 부가 데이터를 추가할 수 있으므로 후행 데이터의 존재만으로 악성이라고 단정하지 않습니다.

---

## <font color="#ff0000">Q43. 압축 폭탄은 어떻게 탐지하나요?</font>

다음 정보를 조합해 압축 폭탄 가능성을 판단합니다.

* 압축파일 크기
* 예상 압축 해제 크기
* 압축률
* 내부 엔트리 수
* 중첩 압축 깊이
* 반복적으로 압축된 파일 존재 여부

압축 해제 크기가 원본보다 지나치게 크거나 중첩 깊이가 설정한 기준을 초과하면 `archive_bomb_suspected` Feature에 반영합니다.

실제 서비스에서는 전체 압축 해제를 시도하지 않고 메타데이터 기반으로 예상 크기를 계산하며 자원 제한을 적용해야 합니다.

---

## <font color="#ff0000">Q44. 암호화된 압축파일은 어떻게 분석하나요?</font>

암호화된 압축파일은 내부 내용을 직접 확인하기 어렵습니다.

따라서 암호화 여부, 파일 크기, 확장자, 헤더, 외부 문자열 등의 제한된 정보만 분석할 수 있습니다. 내부 분석이 불가능하므로 서비스 정책에 따라 업로드 차단, 격리 또는 사용자에게 암호 해제를 요청하는 방식이 필요합니다.

---

## <font color="#ff0000">Q45. 압축파일 내부 경로 순회도 탐지하나요?</font>

`../`, `..\`, 절대경로, 드라이브 경로 등 압축 해제 시 상위 디렉터리로 이동할 수 있는 파일명을 검사할 수 있습니다.

이러한 Zip Slip 유형은 파일 자체가 악성코드가 아니더라도 압축 해제 과정에서 시스템 파일을 덮어쓸 수 있습니다. 따라서 압축 내부 파일명의 경로 정규화와 대상 디렉터리 이탈 여부 검사가 필요합니다.

---

## <font color="#ff0000">Q46. Decompression Bomb 이미지와 압축 폭탄은 어떻게 다른가요?</font>

압축 폭탄은 ZIP 같은 압축파일을 해제할 때 저장공간이나 메모리를 과도하게 소비하게 합니다.

이미지 Decompression Bomb은 작은 이미지 파일이 디코딩될 때 매우 큰 픽셀 배열을 생성하여 메모리와 CPU를 소모하게 합니다. 따라서 이미지에서는 파일 크기뿐 아니라 가로·세로 해상도와 전체 픽셀 수를 제한해야 합니다.

현재 38개 핵심 Feature만으로 이미지 폭탄을 완전히 판단하기 어렵다면 이미지 전용 파서 Feature로 확장하는 것이 필요합니다.

---

## <font color="#ff0000">Q47. 손상된 파일을 파싱하다가 분석 시스템이 공격당할 가능성은 없나요?</font>

가능성이 있습니다. 정적 분석기 자체도 외부 입력을 처리하는 소프트웨어이므로 파서 취약점의 공격 대상이 될 수 있습니다.

실제 서비스에서는 다음 보호가 필요합니다.

* 분석 프로세스 격리
* 최소 권한 실행
* CPU·메모리·실행 시간 제한
* 네트워크 접근 차단
* 파서와 라이브러리 최신화
* 임시 디렉터리 분리
* 파일 크기 및 중첩 깊이 제한

즉, 파일을 실행하지 않는다고 해서 분석 과정이 완전히 안전한 것은 아닙니다.

---

## <font color="#ff0000">Q48. 이미지 메타데이터의 위험 문자열은 왜 검사하나요?</font>

EXIF와 XMP 같은 이미지 메타데이터에는 일반 텍스트를 저장할 수 있습니다.

메타데이터 자체가 항상 실행되는 것은 아니지만, 서버나 애플리케이션이 이를 HTML에 그대로 출력하거나 명령 처리에 사용하면 XSS나 명령 삽입으로 이어질 수 있습니다. 따라서 스크립트 태그, 경로 순회 문자열, 명령어, URL 등의 위험 패턴을 확인할 필요가 있습니다.

---

## <font color="#ff0000">Q49. 파일명에 포함된 경로 순회 문자열도 파일 내용 분석에 포함되나요?</font>

파일 업로드 보안에서는 파일 내용뿐 아니라 파일명도 외부 입력이므로 함께 분석해야 합니다.

예를 들어 `../../shell.php` 또는 `..\..\config`와 같은 파일명은 저장 경로를 이탈할 가능성이 있습니다. 파일명은 basename으로 정규화하고, 저장 시에는 서버가 새 파일명을 생성하며, 최종 저장 경로가 허용 디렉터리 내부인지 확인해야 합니다.

---

## Q50. 서버에서 선언한 MIME 타입만 믿으면 안 되나요?

믿으면 안 됩니다. 클라이언트가 전달하는 `Content-Type`은 쉽게 조작할 수 있습니다.

따라서 다음 정보를 교차 검증해야 합니다.

* 사용자 파일명과 확장자
* 클라이언트가 전달한 MIME 타입
* 서버가 Magic Bytes로 판별한 형식
* 실제 파서가 확인한 내부 구조

---

## Q51. 파일 시그니처만 바꾸면 탐지를 우회할 수 있지 않나요?

단순한 시그니처 기반 탐지만 사용하면 우회할 수 있습니다.

본 프로젝트는 Magic Bytes뿐 아니라 확장자 불일치, 내부 시그니처, 엔트로피, 문자열, 실행 API, 압축 구조 등 여러 Feature를 사용합니다. 따라서 헤더만 변경하는 공격에는 단일 시그니처 방식보다 강합니다.

그러나 고도로 조작된 파일은 여전히 우회할 수 있으므로 파서 기반 구조 검증과 동적 분석을 결합해야 합니다.

---

## <font color="#245bdb">Q52. 악성코드 시그니처나 YARA를 사용했나요</font>?

본 프로젝트의 핵심은 특정 악성코드 해시나 시그니처에 의존하기보다 일반적인 정적 특징을 머신러닝에 입력하는 것입니다.

YARA를 결합하면 알려진 악성 패턴을 빠르게 탐지할 수 있으므로 실서비스에서는 다음과 같은 계층형 구성이 적절합니다.

1. 확장자·크기 정책 검사
2. 해시·YARA·백신 검사
3. 정적 Feature 기반 모델
4. 의심 파일 샌드박스 분석
5. 최종 허용·차단·격리

---

## Q53. 정적 분석 결과가 정상이라면 파일을 바로 허용해도 되나요?

바로 안전하다고 단정해서는 안 됩니다.

정적 분석 결과는 위험도 판단을 위한 하나의 신호입니다. 예측 확률과 서비스 정책에 따라 다음과 같이 처리하는 것이 적절합니다.

* 저위험: 허용
* 중간 위험: 추가 검사 또는 격리
* 고위험: 차단
* 분석 실패·암호화 파일: 정책에 따라 제한

---

# 5. 날카로운 검증 질문

## <font color="#ff0000">Q54. 94개 파일 유형을 지원한다는 것은 모든 형식을 상세 분석한다는 뜻인가요?</font>

아닙니다.

94개 파일 유형이 데이터셋에 포함되어 있다는 의미와 모든 형식에 전용 파서를 제공한다는 의미는 구분해야 합니다. 모든 파일에는 공통 정적 Feature를 적용하지만, 압축파일이나 ZIP 기반 문서처럼 구조 해석이 가능한 형식에는 추가 분석을 수행합니다.

파일 유형별 상세 지원 범위는 별도로 명시하는 것이 정확합니다.

---

## Q55. 파일 경로가 Feature에 포함되면 데이터 출처가 노출되지 않나요?

파일 경로 자체는 모델 입력 Feature에서 제외해야 합니다.

경로는 데이터 관리와 오류 추적을 위한 manifest에는 저장할 수 있지만, 모델에 입력하면 `benign`, `malware`, 데이터셋 이름 등의 문자열이 라벨을 직접 노출할 수 있습니다. 이는 심각한 정보 누수입니다.

---

## Q56. 파일 크기가 데이터셋마다 다르면 출처를 구분하는 Feature가 되지 않나요?

그럴 수 있습니다.

특정 데이터셋의 파일 크기 범위가 고정되어 있으면 모델이 악성 구조가 아닌 크기 분포를 학습할 수 있습니다. 따라서 출처별 파일 크기 분포를 비교하고, 크기 구간별 성능 또는 파일 크기 Feature를 제거한 비교 실험이 필요합니다.

---

## Q57. 악성 파일을 직접 보관하고 분석하는 것이 안전한가요?

원본 악성 파일은 암호화된 보관소 또는 접근이 제한된 디렉터리에 저장해야 합니다.

분석 환경에서는 다음 원칙을 적용해야 합니다.

* 실행 권한 제거
* 자동 미리보기 비활성화
* 네트워크 차단
* 최소 권한 사용
* 해시값 기반 식별
* 압축 해제 및 삭제 절차 통제
* Git 저장소에 원본 악성 파일 업로드 금지

---

## <font color="#245bdb">Q58. 재현성을 어떻게 보장했나요?</font>

다음 정보를 기록하면 재현성을 확보할 수 있습니다.

* 데이터 출처 URL
* 수집 날짜
* 파일 SHA-256
* 원본 라벨
* 변환된 라벨
* 전처리기 버전
* Feature 스키마와 순서
* 분석 성공·실패 여부
* Mitra 원본·페이로드·생성 결과 관계
* 학습·검증·평가 분할 기준
* 랜덤 시드

특히 생성 데이터는 동일한 원본과 페이로드를 추적할 수 있도록 manifest를 유지해야 합니다.

---

## Q59. 가장 큰 한계는 무엇인가요?

가장 큰 한계는 세 가지입니다.

첫째, 정적 분석이므로 실행 시점의 악성 행위를 직접 확인할 수 없습니다.

둘째, 데이터셋의 확장자 및 출처 분포가 불균형하여 모델이 실제 악성 행위보다 데이터 출처나 파일 유형을 학습했을 가능성이 있습니다.

셋째, Image Anomaly 데이터 중 일부가 Mitra로 생성되었기 때문에 생성 도구의 특징이 모델에 반영됐을 수 있습니다.

---

## Q60. 향후 가장 먼저 개선해야 할 부분은 무엇인가요?

우선순위는 다음과 같습니다.

1. SHA-256 및 원본 그룹 기준 중복 제거
2. 확장자·출처 단위 학습·평가 분리
3. 파일 유형별 Precision·Recall 산출
4. 확장자 관련 Feature 제거 비교 실험
5. 독립 외부 데이터셋 검증
6. 실제 Polyglot 및 이미지 파서 CVE 표본 추가
7. HWP·HWPX와 중첩 압축파일 분석 강화
8. YARA·백신·샌드박스를 결합한 다단계 탐지

# 6. 발표자가 반드시 기억할 핵심 답변

질문이 길거나 예상하지 못한 경우에는 다음 원칙을 중심으로 답변하면 됩니다.

* “정적 분석 결과는 악성 여부를 확정하는 절대적인 기준이 아니라 여러 특징을 결합한 위험도 판단 결과입니다.”
* “확장자나 Magic Bytes 하나만으로 판단하지 않고 파일명, 형식, 바이트, 문자열, 압축 구조를 함께 분석했습니다.”
* “Mitra 생성 데이터는 실제 공격 데이터를 완전히 대체하는 것이 아니라 부족한 Image Anomaly 유형을 보완하기 위해 사용했습니다.”
* “실서비스에서는 정적 분석 모델뿐 아니라 정책 검사, YARA·백신 및 동적 분석을 결합해야 합니다.”
* “향후에는 동일 출처 분리와 외부 데이터 검증을 통해 일반화 성능을 확인할 계획입니다.”
